# 협업 가이드 (CONTRIBUTING)

이 문서는 팀의 Git/GitHub 협업 규칙을 정리한 것입니다. 모든 팀원은 작업 전에 한 번 읽어 주세요.

---

## 1. 브랜치 전략: GitHub Flow

- `main`: 항상 배포 가능한 상태입니다. 어떤 시점에 받아도 깨지지 않아야 합니다.
- 작업 브랜치: 모든 작업은 `main`에서 새 브랜치를 따서 진행하고, PR로 `main`에 병합합니다.
- `main` 직접 push는 금지이며, Branch Protection으로 막혀 있습니다. 병합에는 최소 1명의 승인이 필요합니다.

**GitHub Flow를 선택한 이유**
> 브랜치가 `main` + 작업 브랜치뿐이라 규칙이 단순해서, Git 협업이 처음인 팀도 바로 따라 할 수 있습니다.
> 릴리스 주기가 따로 없는 소규모 프로젝트라 `develop`·`release` 브랜치(Git Flow)가 필요 없습니다.
> 모든 변경이 PR을 거치므로 리뷰와 이슈 추적이 자연스럽게 강제됩니다.

### 브랜치 네이밍 규칙

```
<type>/<이슈번호>-<짧은-설명>
```

| type | 용도 | 예시 |
|---|---|---|
| `feature` | 새 기능, 결과물 추가 | `feature/3-add-slugify` |
| `fix` | 버그 수정 | `fix/7-slugify-empty-string` |
| `docs` | 문서만 수정 | `docs/5-update-readme` |
| `refactor` | 동작 변화 없는 구조 개선 | `refactor/9-split-utils` |
| `chore` | 설정, 빌드, 기타 | `chore/2-add-gitignore` |

- 설명은 **영어 소문자 + 하이픈(kebab-case)** 으로 3~5단어 이내로 씁니다.
- 이슈 번호는 반드시 넣습니다. 브랜치만 보고도 어떤 이슈의 작업인지 알 수 있어야 합니다.
- 병합된 브랜치는 삭제합니다.

## 2. 커밋 메시지 컨벤션

```
<type>: <무엇을 (왜) 바꿨는지>
```

| type | 의미 |
|---|---|
| `feat` | 새 기능 추가 |
| `fix` | 버그 수정 |
| `docs` | 문서 수정 |
| `refactor` | 동작 변화 없는 코드 구조 개선 |
| `test` | 테스트 추가, 수정 |
| `chore` | 설정, 폴더 구조, 기타 잡무 |

- 제목은 한국어 또는 영어로, 50자 안팎으로 씁니다.
- 필요하면 한 줄을 띄우고 본문에 "왜" 바꿨는지 자세히 적습니다.
- 커밋 하나에는 논리적 변경 하나만 담습니다.

### 의미없는 커밋 메시지 (금지)

아래 중 하나라도 해당하면 의미없는 메시지로 간주하고, 리뷰에서 수정을 요청합니다.

1. **변경 대상을 유추할 수 없는 단어만 있는 경우**: `update`, `fix`, `temp`, `wip`, `final`, `수정`
2. **무엇을/왜 바꿨는지 드러나지 않는 경우**: `bug fix`, `edit file`, `코드 수정` (구체적인 대상이나 효과 없음)

| ❌ 나쁜 예 | ✅ 좋은 예 |
|---|---|
| `fix` | `fix: slugify가 연속 공백을 하이픈 여러 개로 바꾸던 문제 수정` |
| `update README` | `docs: README에 유틸 함수 사용 예시 추가` |
| `wip` | `feat: chunk_list 함수 기본 구현 추가` |

> 이미 push 전이라면 `git commit --amend`로 메시지를 고칠 수 있습니다. ([troubleshooting-log.md](troubleshooting-log.md) 참고)

## 3. 이슈와 PR 작성 규칙

### 이슈
- 모든 작업은 **Issue를 먼저 만들고** 시작합니다.
- 제목에는 할 일을 한 문장으로 씁니다. (예: `문자열 slugify 함수 추가`)
- 담당자(Assignee)를 본인으로 지정합니다.

### PR
- 모든 작업 브랜치는 PR로 `main`에 병합합니다.
- PR 본문에는 아래 항목을 반드시 포함합니다. 템플릿(`.github/pull_request_template.md`)이 자동으로 채워집니다.

| 항목 | 내용 |
|---|---|
| 관련 이슈 | `Closes #이슈번호` (또는 `Fixes #`). 병합 시 이슈가 자동으로 닫힙니다. |
| 변경 사항 (What) | 무엇을 바꿨는지 |
| 변경 이유 (Why) | 왜 바꿨는지 |
| 테스트/검증 방법 (How) | 리뷰어가 어떻게 확인할 수 있는지 |

- PR 하나에는 이슈 하나만 다룹니다. 크기가 작을수록 리뷰가 쉽습니다.
- 병합 방식은 **Create a merge commit**을 기본으로 합니다.

## 4. 코드 리뷰 규칙

### 리뷰어
- PR이 올라오면 가능하면 24시간 안에 리뷰합니다.
- **"LGTM", "좋아요"만 남기는 리뷰는 인정하지 않습니다.** 실질 코멘트를 1개 이상 남깁니다.
  - 특정 라인이나 파일을 근거로 한 질문: "빈 문자열이 들어오면 어떻게 되나요?"
  - 대안 제안: "여기는 `str.join`을 쓰면 더 간단할 것 같습니다."
  - 리스크 지적: "이 변경으로 기존 호출부의 반환 타입이 바뀝니다."
  - 개선 제안: 이름, 가독성, 예외 처리 등
- 문제가 있으면 **Request changes**, 괜찮으면 **Approve**를 누릅니다.

### 작성자
- 리뷰 코멘트에는 반드시 **답글 또는 수정 커밋**으로 응답합니다.
  - 반영했다면 수정 커밋을 push하고, "`abc1234`에서 반영했습니다"처럼 커밋을 언급합니다.
  - 반영하지 않는다면 이유를 답글로 남깁니다.
- 리뷰어와 작성자 사이에 **최소 1회의 상호작용(답글, 수정 반영)** 이 기록으로 남아야 합니다.
- 승인을 받은 뒤 작성자가 직접 병합하고 브랜치를 삭제합니다.

## 5. 충돌 발생 시 대응 흐름

| 단계 | 누가 | 어떻게 |
|---|---|---|
| 1. 발견 | PR 작성자 | PR에 "This branch has conflicts"가 표시되면 작성자가 해결을 맡습니다. |
| 2. 최신화 | PR 작성자 | 로컬에서 `git fetch origin` 후 `git merge origin/main`을 실행합니다. |
| 3. 해결 | PR 작성자 | 충돌 마커(`<<<<<<<`, `=======`, `>>>>>>>`)를 확인하고, 양쪽 의도를 모두 살리도록 편집합니다. 판단이 어려우면 상대 변경의 작성자에게 PR 코멘트로 물어봅니다. |
| 4. 검증 | PR 작성자 | 마커가 남지 않았는지, 코드가 정상 동작하는지 확인한 뒤 `git add` → `git commit` → `git push` 합니다. |
| 5. 기록 | PR 작성자 | [conflict-resolution.md](conflict-resolution.md)에 충돌 유형, 원인, 해결 과정, 해결 전 마커 원본을 기록합니다. |
| 6. 재리뷰 | 리뷰어 | 해결 결과를 다시 확인한 뒤 승인합니다. |

- 충돌 해결 중 꼬였다면 `git merge --abort`로 병합 전 상태로 되돌린 뒤 다시 시도합니다.
- `main`에 force push하는 것은 금지입니다.
